# Popo v0.9.1

Version 0.9.1 expands consumer adoption examples, strengthens regression tests and corrects source
and test documentation. This patch release record is prepared in released form for 2026-10-24;
tagging and publication are separate operations and have not been performed for this candidate.
Release readiness is blocked by the current validation failure recorded below.

## Change Scope

Add independently copyable AWS CDK (in Python), Python, and Swift consumers under `examples/swift/`,
`examples/python/` and `examples/cdk/`, with an index and complete setup instructions. Each consumer
owns one explicit `popo.toml` profile, a Make target, a whole-repository pre-commit hook, pinned
tool inputs and a complete CI workflow. The entry points delegate to `make guardrails`, which runs
`popo check-all --profile guardrails`. Retain conventional Markdown filenames and shorten the
preparation-only Swift example directory to `examples/swift/`.

Keep consumer-specific policy differences: Swift selects language-neutral checks, Python compares
bounded runtime dependencies with minimum constraints, and Python CDK compares exact application
pins. Both Python consumers check declared interpreter and mypy/Ruff consistency. Application tests
and local CDK synthesis remain separate commands; guardrails never import the CDK application,
require AWS credentials or deploy resources.

Share example-copy, expected-check and drift fixtures across deterministic CLI integration tests and
installed-artifact acceptance tests. Exercise real Make, installed Git hooks triggered by commits in
disposable repositories, and the workflow command locally for each wheel and sdist. Verify shared
policy failures, Make recipe, hook argument, CI invocation and working-directory drift, and
unchanged consumer source bytes. Check Python/CDK declaration drift independently of valid wiring.

Extract reusable installed-process helpers and artifact-installation fixtures. Expand `make
test-installation` from one module to the entire e2e directory so the new acceptance suite runs with
existing installation contracts. Update contributor-facing workflow, test and adoption guides.
Popo's runtime behavior and package metadata are unchanged relative to v0.9.0; source changes affect
docstrings only. These are adoption, documentation and validation improvements rather than new
checker capabilities.

Consolidate guardrail drift scenarios, share hook metadata parsing, and reuse temporary UTF-8 file
writers. Strengthen hosted and automation configuration diagnostics and compare consumer file
snapshots after validation. Keep unit suites as pytest class instance methods and preserve existing
docstring and comment details.

Exercise malformed dependency inputs in both exact and minimum-constraints modes. Check automation
configuration from both standalone popo.toml and Python metadata. Run malformed Python and
undecodable-header scenarios independently, and model Git discovery explicitly in header tests
rather than depending on installed Git or inherited configuration.

Inspect actionlint's copied workflow and implicit configuration while its temporary view exists.
Check exclusion of unrelated consumer files, exact tool statuses, cleanup, and preservation of
original inputs. Add process-launch cleanup coverage; current validation exposes a missing ci.yml
fixture in that test, so this record does not claim that scenario passes.

Correct test descriptions of expected diagnostics, regular-expression matching, policy sources,
fixture parameters and artifact selection. Clarify source contracts for pin syntax, header newline
handling, configuration construction, API response data, JSON serialization and propagated errors.
Document the existing dependency-metadata path and Markdown URL-parsing ValueError behavior rather
than changing exception handling. Update the test guide to describe fixture isolation and
assertions.

## Compatibility and Configuration

Existing CLI commands, configuration schemas, output formats, exit codes, public exports and runtime
dependencies retain their v0.9.0 contracts. Existing consumers need no policy migration. The
examples demonstrate explicit profiles; bare `check-all` retains legacy defaults and does not infer
a profile from the consumer language. Each example is self-contained and may be adapted without
importing neighboring examples or Popo's contributor Makefile.

The contributor installation target now collects all e2e modules. `INSTALLATION_TEST_PATH` and
`INSTALLATION_TEST_ARGS` remain available for deliberate selection overrides. Example application
pins belong to those consumers and do not change Popo's runtime dependency bounds. Their guardrail
tool files intentionally pin an existing immutable v0.9.0 revision; they do not assume v0.9.1 has
already been tagged or published.

### Breaking Changes

No supported CLI or configuration interface is removed or changed. Contributors running `make
test-installation` receive additional POSIX example execution coverage and may download the
examples' pinned pre-commit runner. References to the preparation-only `examples/swift-guardrails/`
path should use `examples/swift/`; that earlier path is not part of the v0.9.0 tagged tree.

### Deprecations

No deprecations are introduced in this release.

## Support Boundary

Popo continues to require Python `>=3.13,<3.15`, with unchanged wheel/sdist formats and publication
safeguards. The runnable Make/Git-hook examples require a POSIX shell, Git and Make. Windows retains
native installed-CLI coverage and skips the example execution suite. Swift compilation and CDK
application behavior are separate from generic repository validation; no new Swift toolchain, cloud
deployment or infrastructure semantic support is promised by this patch.

## Deployment and Rollback

The [release policy] and [release operations] govern separately authorized tagging and optional
publication. Versions derive from Git through `setuptools-scm`; this preparation does not create a
tag, publish a release or modify hosted settings. Preserve existing immutable tags.

No data migration or hosted configuration change is required. Adopt an example alongside existing
controls before replacing them. To roll back adoption, restore the previous verified consumer pin
and local validators; restore replaced Make/hook/workflow declarations through review. Contributors
can restore a deliberate installation-test selection through the existing Make overrides.

## Known Limitations and Follow-Up

The actionlint launch-cleanup test must prepare its selected ci.yml input before expecting a process
startup failure. Without that fixture, validation fails during source reading and never exercises
the mocked launch. Correct the test setup and rerun the full release gate before release closeout.

Malformed bracketed Markdown URLs can propagate ValueError from URL parsing. Dependency metadata
outside the consumer root can propagate ValueError from shared configuration path handling. This
patch documents these existing behaviors; converting them into reported diagnostics requires a
separate implementation change and regression tests.

The acceptance suite executes the consumer workflow command locally; it does not run GitHub's
scheduler, setup actions, hosted checks or branch protections. It substitutes built Popo artifacts
for the examples' Git dependency pins, so installation from those pins is a separate verification.
Static parity does not establish hook installation, trigger coverage, absence of skips or failure
suppression, tool-version equivalence, or arbitrary shell equivalence.

Complete final committed-tree validation, tag/version agreement and hosted cross-platform checks
before release closeout. Record publication evidence only if separately authorized. No AWS
bootstrap, deployment, destruction or cloud access is part of release preparation.
