# Popo v0.1.1 (Planned)

The planned version 0.1.1 aligns Popo's declared `packaging` minimum and lowest-dependency test pin
at 26.3. The [changelog] prepares this release for 2026-09-24; no local `v0.1.1` tag exists at
preparation time. This document does not assert publication.

## Highlights

- Makes package metadata and the lowest-dependency fixture agree on `packaging` 26.3.
- Excludes the minimum-version fixture from routine Dependabot version updates while retaining
  updates to package metadata.
- Adds regression coverage and contributor guidance for coordinated minimum-version changes.

## Change Scope

The candidate updates `pyproject.toml`, `requirements/lowest.txt`, Dependabot configuration,
dependency-policy and automation tests, and public documentation. It resolves the quality-gate
failure caused by upgrading the fixture to 26.3 while metadata still declared a 25.0 minimum.

No Popo checker implementation, CLI command, flag, configuration key, diagnostic format, or
exit-code contract changes. Repository checks remain read-only; workflow permissions and publication
gates are unchanged.

## Compatibility and Configuration

### Minimum Dependency Change

`packaging>=26.3,<27` replaces `packaging>=25.0,<27`. Versions below 26.3 are no longer supported.
Consumers with older `packaging` pins must update their environment constraints before adopting this
release. Normal dependency resolution installs a compatible version unless another constraint
conflicts. The upper bound remains below 27.

The lowest-dependency fixture now contains `packaging==26.3`. Future intentional minimum increases
must change both metadata and fixture together; see the [contributing guide]. This fixture is not a
lockfile that should independently track the newest available version.

## Support Boundary

Python 3.13 and 3.14 support is unchanged. The compatibility change is limited to the declared
`packaging` minimum; there is no new cloud, credential, or consumer-language requirement.

## Validation

The final candidate commit is pending because release changes are still uncommitted at preparation
time. Before tagging, record that commit and validation evidence for:

- `make check`, including regression cases for matching pins, mismatched minimums, and the
  Dependabot exclusion;
- `make docs-markdown` and `make release-changelog RELEASE_VERSION=v0.1.1`;
- `make check-release`, including both distributions, `twine check`, and clean installations; and
- hosted dependency-boundary and cross-platform checks required by the [release policy].

Development-checkout results do not establish that the final tagged artifacts pass. No hosted
release, artifact-integrity, or publication result is asserted here.

## Deployment and Rollback

Merging does not deploy cloud resources. Pushing an annotated tag triggers CD validation; GitHub
publication still requires manual opt-in and the safeguards in the [release policy]. PyPI
publication remains unconfigured.

Before release, correct the candidate if validation fails. After release, prefer a follow-up version
rather than moving the tag. If a consumer cannot satisfy the new minimum, it can retain its prior
validated Popo version and environment while resolving the constraint conflict. Read-only checks
require no consumer-data migration or rollback.

## Known Limitations and Follow-Up

- The Dependabot exclusion prevents routine version updates to the fixture; intentional minimum
  changes still require coordinated maintainer edits and CI validation.
- Confirm the candidate commit and date, run the complete release gates, and reconcile generated
  GitHub Release notes with this record before publication.
