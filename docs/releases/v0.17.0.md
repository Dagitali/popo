# Popo v0.17.0

Version 0.17.0 extends opt-in Apple metadata contracts and streamlines validation and regression
suites. This minor release is dated 2026-11-05 and documented in released form at the maintainer's
request. Tagging and publication remain separate operations.

## Highlights

Use all-configuration scope, typed optional expectations, required-anywhere keys, forbidden key
patterns and explicit discovered-file coverage with `popo check-apple-metadata`. See the [metadata
guide] for examples and boundaries, and the [changelog] for complete dated scope.

## Change Scope

Inspect every declared Xcode build configuration, including unreferenced objects, when explicitly
requested. Validate optional values only where present, require selected keys somewhere in the
selected mappings and search top-level keys for forbidden regular expressions. Require discovered
files to be covered by explicit plist rules through confined, nonrecursive filename discovery.
Missing directories, unreadable discovery, escaping symlinks and uncovered matches fail privately.

Reuse compiled key patterns during configuration contradiction checks and validation. Combine
positive-key sets directly and stream expected values without tuple copies. Preserve validation
order, substring matching, typed comparisons and redacted diagnostics.

Consolidate metadata configuration and integration cases into their existing modules with focused
classes, retaining every case and docstring. Assert exact ordered JSON findings, command identity,
pass fields and unchanged inputs, and guard aggregate-check process creation through Popen.

## Compatibility and Configuration

The new optional policies justify a minor bump from v0.16.0. Existing metadata selection and default
profiles retain their contracts. New fields require v0.17.0 or later and explicit consumer policy;
they do not implicitly enable discovery or all-configuration inspection. Reporting schemas and exit
codes remain unchanged. Distribution versions continue to derive from Git through `setuptools-scm`.

### Breaking Changes

No intentional command, configuration or runtime removal is introduced. New policies reject unsafe
or contradictory expectations and ambiguous discovery selectors. Existing target/project scope
continues to follow its named configuration lists; all-configuration scope deliberately includes
unreferenced configuration objects and forbids target/named-configuration selectors.

### Deprecations

No new deprecation or support-window commitment is introduced. Internal modules remain
implementation details; consumers should adopt the public CLI.

## Support Boundary

Popo requires Python >=3.13,<3.15. Metadata checks remain offline and read-only, without Apple
tools, signing credentials or deployed services. Discovery selects literal directories and filename
globs, never recursive traversal or directory globs. Diagnostics omit native values and exception
text.

### Artifact Contracts

The distribution remains `popo`, with the `popo` console script and `python -m popo` entry point.
Validate fresh wheel and source distributions, Twine metadata and clean installations. Development
SCM versions do not establish metadata produced by the eventual immutable v0.17.0 tag.

## Deployment and Rollback

Follow the [release policy] and [release operations] for separately authorized tagging and optional
publication. This preparation creates no tag or hosted release and publishes no package. No data
migration is required. Adopt a reviewed immutable dependency pin and explicit consumer policy; roll
back by restoring the prior verified pin and compatible policy.

## Known Limitations and Follow-Up

Checks inspect literal source settings, not resolved Xcode builds or signed application contents.
They do not expand variables, resolve xcconfig inheritance, inspect signatures or archives, validate
schemes/test plans, approve evidence or publish releases. Forbidden-key regexes inspect top-level
keys; discovery coverage does not establish the validity of a built artifact. Consumer-native build,
signing and deployment checks remain necessary.

Rebuild and validate the final committed/tagged tree, intended version and release record before
delivery. Local validation does not establish hosted Linux/Windows or Python 3.13 success.
