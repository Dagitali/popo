# Popo v0.3.6

Version 0.3.6, tagged on 2026-10-01 (UTC), validates release records before reviewed integration and
corrects missing release history. This patch release covers the complete
`feature/validate-release-records` change set since `v0.3.5`, plus its release preparation. The tag
does not establish hosted validation or publication. See the [changelog].

## Highlights

See the [changelog] for this version's concise change list.

## Change Scope

The PR workflow adds a read-only checkout with `contents: read` and persisted credentials disabled.
Its Python gate checks release history without executing documents or publishing. Unit tests
exercise successful and failing PR and merge-group scenarios. README, contributor, workflow-map, and
branch-protection guidance explain the new gate and activation boundary.

The 0.3.5 record was committed after its tag. This correction preserves the tag and records current
checkout evidence separately from historical release validation. The 0.3.6 preparation adds this
record, its dated changelog section, and the archive entry.

## Compatibility and Configuration

No CLI, consumer-configuration, or runtime dependency changes. No consumer migration is required.

Branches named `release/MAJOR.MINOR.PATCH` or `hotfix/MAJOR.MINOR.PATCH`, optionally with `v` on the
version, require a matching candidate entry. Other source names retain the configured routing policy
and can accumulate changes under `Unreleased`. Merge groups recheck combined release history and
inherit candidate-version validation from queued PRs.

Hosted blocking requires the emitted check to be required by an active ruleset. The prepared ruleset
for `main` and `develop` was created disabled, with no bypass actors; it must be verified and
activated after successful hosted validation. See the [branch-protection guide].

## Support Boundary

No supported-Python or package dependency changes. These repository-specific workflow checks do not
add release-document policy to Popo's reusable consumer CLI.

## Validation

Interpret these results using the [evidence boundaries].

Local validation on 2026-10-01 passed against the 0.3.6 working-tree candidate:

- `make release-changelog RELEASE_VERSION=v0.3.6` found the matching dated entry.
- `make docs-markdown` passed local links and heading anchors.
- The PR release-record script passed locally with `release/0.3.6` as its candidate source.
- `make check-release` with a fresh temporary `PYTHON_DIST_DIR` passed lint, formatting, strict
  typing, all 286 unit/integration tests, repository checks, wheel/source builds, `twine check`, and
  all 18 artifact/clean-installation tests.
- `git diff --check` passed.

The first isolated build could not resolve PyPI within the network-restricted sandbox; rerunning
with network access passed the full release gate. Built artifacts have a Git-derived development
version rather than final `0.3.6`. These results do not establish the eventual tag's version, hosted
cross-platform success, active merge enforcement, or publication. This validation wording was added
after the artifact run and rechecked with the Markdown and changelog gates.

## Deployment and Rollback

Shared tagging and publication rules are in [release operations].

If the gate blocks a valid candidate, correct its record or the validator through reviewed work.
Coordinate required-check changes using the branch-protection transition procedure, preserve
existing protections, and issue a subsequent correction rather than moving release tags.

## Known Limitations and Follow-Up
