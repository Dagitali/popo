# Popo v0.12.0

Version 0.12.0 adds native test-result acceptance and consumer-owned Python/Swift architecture
boundaries. This minor release is dated 2026-10-27 and documented in released form at the
maintainer's request. Tagging and publication remain separate operations.

## Highlights

See the [changelog] for dated scope and [result and boundary checks] for configuration and adoption.
Use one explicit policy from Make, pre-commit and CI; the existing parity checker continues to
inspect entry-point declarations without invoking them.

## Change Scope

Add `check-test-results` for exported Xcode-summary JSON. Validate count types, arithmetic, runtime
warning collections and consumer-selected acceptance thresholds. Support explicit artifact-root or
single-summary selection without exposing report contents or accepting a passing sibling in place of
failed evidence.

Add `check-python-boundaries` and `check-swift-boundaries` with consumer-named layers, confined file
selection, import allowlists, forbidden layers and explicit forbidden symbols. Python resolves
static imports and relative package names through AST inspection. Swift uses masked lexical imports
and declared type tokens. Both integrate with profiles, aggregate continuation and text/JSON
results. Fix ownership of root-level `src.py` without confusing it with a `src/` layout directory.

Share boundary configuration and orchestration through a generic analyzer protocol, while retaining
native parsing and ownership rules. Share documentation iteration, callable evidence dispatch and
post-parse source evaluation through typed callbacks. Remove redundant boundary type aliases and
clarify runtime/compiler observations. Validate guardrail profiles from the same configuration
snapshot as their entry points and reuse common source/log pattern validation.

Modernize tests through isolated policy fixtures, parameterized native-language cases, exact
finding-order assertions and verified read-once behavior. Keep shared configuration tests in their
own layer and unit tests in class suites. Preserve detailed docstrings, comments and complete
statement/branch coverage without adding unnecessary inheritance.

## Compatibility and Configuration

The new optional commands justify a minor bump from v0.11.0. Distribution versions remain derived
from Git through setuptools-scm; no second version source is introduced. Configure `test-results`,
`python-boundaries` or `swift-boundaries` explicitly, or select the corresponding public commands
through an existing check profile. Configured optional domains participate in implicit selection;
explicit check lists and profiles retain their existing selection behavior.

### Breaking Changes

No intentional public CLI, package-root export or supported-runtime removal is introduced. Unsafe
source/log patterns still fail configuration, with diagnostics now identifying the specific include
or exclude setting. Internal boundary aliases were removed in favor of the shared model; these
checker internals are not a promised consumer API. Consumers should use the documented CLI.

### Deprecations

No new deprecation window or long-term support commitment is introduced.

## Support Boundary

Popo requires Python >=3.13,<3.15. Checks remain offline and read-only: they do not execute consumer
source, compile Swift, run tests, export Xcode bundles or invoke arbitrary adapters. Xcode-summary
validation accepts exported JSON rather than native result bundles; compiler validation and test
execution remain consumer responsibilities.

Python boundary checks do not resolve dynamic imports, re-export chains, alternate package roots or
local alias shadowing. Swift checks remain conservative lexical guards, not SwiftSyntax or
compiler-based semantic isolation. Their documented limitations remain purposeful. No Tree-sitter or
SwiftSyntax dependency is introduced by this release.

### Artifact Contracts

The distribution remains `popo`, with the `popo` console script and `python -m popo` entry point.
Validate wheel and sdist plus clean installed console/module commands. Native check-result JSON
remains separate from source-inventory and hosted-audit evidence. No publishing, hosted workflow
dispatch or repository-setting changes are part of preparation.

## Deployment and Rollback

Follow the [release policy] and [release operations] for separately authorized tagging and optional
publication. Tags remain immutable. This preparation creates neither a release tag nor a hosted
release and does not publish packages.

No consumer data migration is required. Adopt optional checks with a reviewed immutable dependency
pin and explicit policy, verifying positive and negative cases across local and CI entry points. To
roll back, restore the prior verified dependency pin and policy together.

## Known Limitations and Follow-Up

Final committed/tagged-tree version agreement and supported-platform hosted validation remain
separate delivery requirements. Local success does not establish cross-platform support or
publication. Retain native compiler, test, packaging and integration checks appropriate to each
consumer repository.
