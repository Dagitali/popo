# Popo v0.2.0

Version 0.2.0, tagged on 2026-09-26 (UTC), expands checker capabilities and tightens validation
while preserving Popo's read-only, language- and cloud-neutral role. It covers changes since
`v0.1.5`; see the [changelog].

## Highlights

- Check Markdown reference destinations and explicit HTML anchors, while ignoring fenced examples.
- Reject local link destinations outside the repository, including encoded paths and symlinked
  targets; stop silently excluding maintained paths such as `docs/building.md`.
- Accept commented dependency requirements and block-list Python-version matrices.
- Add the existing quality gate to the installed pre-push hook stage.
- Expand documentation from a project overview into configuration, testing, adoption, development,
  architecture, release, and operational guidance.

## Change Scope

Markdown checks now accept plain directory links, resolve directory fragments through `README.md`,
and check fragments only for Markdown targets. Anchor caching avoids repeated reads within a check
without persisting stale results between runs. Source discovery excludes `node_modules` and matches
ignored directory names by path component.

Dependency checks accept whitespace-delimited inline comments without stripping URL fragments;
installer directives remain unsupported. Python-policy checks inspect contiguous block-list matrices
as well as inline lists. Action checks reject references with an empty action name even when the
revision is a full commit SHA.

Contributor changes include editor and Git conventions, accurate file headers and public docstrings,
expanded regression tests, higher development-tool minimums, aligned Ruff hooks, and the pre-push
quality gate. The package description and documentation metadata now emphasize reusable repository
checks. `NOTICE` clarifies the existing MIT license without changing it. The [documentation index]
links the new guides, playbooks, runbooks, and templates.

## Compatibility and Configuration

Command names, flags, configuration keys, and success/failure exit-code conventions are unchanged.
Diagnostic coverage is broader, so existing repositories can produce additional failures.

### Stricter Validation and Required Review

- Fix broken reference-link definitions, including unused definitions previously skipped.
- Replace local destinations outside the selected repository with valid in-repository links or
  appropriate external URLs. Encoded parent paths and symlinked link targets do not bypass this
  boundary; this is link validation, not a general filesystem sandbox.
- Review Markdown files previously skipped by the `docs/build` substring exclusion.
- Correct invalid or unsupported Python versions in newly inspected block-list matrices.
- Supply a nonempty remote action name as well as a full 40-character commit SHA.

Run `popo check-all` against each consumer before upgrading its CI pin. Consult the [configuration
reference] for check boundaries rather than assuming full Markdown or workflow-expression parsing.
Contributors should refresh `.[dev]` dependencies and use `make hooks` to install or refresh hooks
when desired; installing Popo in a consumer does not install this repository's hooks.

## Support Boundary

Python remains `>=3.13,<3.15`, with runtime dependency `packaging>=26.3,<27`. No cloud credentials
or consumer programming language are required by the general repository checks. Python-specific
checks continue to use consumer-configured policy rather than imposing Popo's development
configuration.

Development minimums increase to build 1.6.1, mypy 2.3.1, pre-commit 4.6.2, pytest 9.1.1, pytest-cov
7.1.0, PyYAML 6.0.3, Ruff 0.16.9, and Twine 7.0.0; existing upper bounds remain. These are
contributor tools, not new runtime dependencies.

## Deployment and Rollback

No cloud deployment, data migration, or automatic PyPI publication is introduced. Merging makes the
source changes available; an authorized annotated tag triggers release validation. Optional GitHub
publication retains the existing manual opt-in and environment safeguards in the [release policy].

If adoption uncovers a regression, restore the consumer's previously validated Popo pin or artifact
and re-run its checks. This also restores the older checker limitations. Preserve existing tags and
use a new release for corrections rather than moving a published tag.

## Known Limitations and Follow-Up

- Markdown checks do not validate external URL availability, undefined reference labels, or inline
  image links, and are not a complete Markdown parser.
- Workflow policy checks statically resolve supported version forms, not arbitrary expressions.
- Local-action and container-reference exemptions remain; the action check does not establish
  container-image immutability.
- Confirm the version and release date, complete artifact and hosted validation, and update this
  record and archive status before claiming release completion.
