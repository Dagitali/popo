# Popo v0.1.4 (Planned)

Version 0.1.4 is prepared for 2026-09-24 to correct the missing release-history entry that caused CD
validation of `v0.1.3` to fail. This candidate adds its own dated changelog section and
retrospectively documents 0.1.3 without changing that tag.

- [Compatibility and Configuration](#compatibility-and-configuration)
- [Support Boundary](#support-boundary)
- [Validation](#validation)
- [Deployment and Rollback](#deployment-and-rollback)
- [Known Limitations and Follow-Up](#known-limitations-and-follow-up)

## Highlights

- Adds the exact `## [0.1.4] - 2026-09-24` heading required by the release-changelog checker.
- Backfills 0.1.3's Commitizen v4.18.1 and Ruff v0.16.8 hook updates in the [changelog].
- Distinguishes a corrected new release from an unchanged historical tag with failed CD validation.

## Change Scope

Changes are limited to the changelog and release documentation. No checker implementation, tests,
dependency bounds, hook versions, or workflow behavior changes relative to `v0.1.3`.

The original `v0.1.3` tag points to `8e0d3e4876a6916da533177b17a48403fd95e9cf`, which lacks its
dated changelog section. CD checks out the selected tag before validating the changelog, so editing
the current branch cannot repair a rerun against that historical tree. The correction must be
included in the commit selected for the new `v0.1.4` tag.

## Compatibility and Configuration

No CLI, configuration, diagnostic, or exit-code changes. The dependency range remains
`packaging>=26.3,<27`. Consumer configuration requires no migration.

## Support Boundary

Python 3.13 and 3.14 support and read-only checks are unchanged. No new cloud or credential
requirements are introduced.

## Validation

Before tagging the final candidate, run:

```console
make release-changelog RELEASE_VERSION=v0.1.3
make release-changelog RELEASE_VERSION=v0.1.4
make docs-markdown
make check-release
```

The 0.1.3 check above validates the retrospective entry in the current checkout, not the original
tag. Record the final candidate commit and repeat applicable hosted gates against it. Development
builds do not prove the eventual tagged version or artifact integrity.

## Deployment and Rollback

Do not move or reuse `v0.1.3`. After review and validation, a separately authorized annotated
`v0.1.4` tag must point to a commit containing these corrections and reachable from the default
branch, as required by the [release policy].

Tag pushes trigger validation only; GitHub publication remains a separate manual opt-in. PyPI
publication and cloud deployment are not configured. No consumer-data rollback is needed; correct
any further release-documentation problems in a follow-up version rather than moving a tag.

## Known Limitations and Follow-Up

- Rerunning CD for the unchanged `v0.1.3` tag will still encounter its missing changelog section.
- Confirm the final release date, candidate commit, distribution checks, and hosted validation
  before finalizing this planned record. No publication result is asserted here.
