# Popo v0.1.0 (Planned)

Version 0.1.0 introduces the repository-policy CLI and its development and release workflows. See
the [changelog] for the release entry.

- [Highlights](#highlights)
- [Change Scope](#change-scope)
- [Compatibility and Configuration](#compatibility-and-configuration)
- [Support Boundary](#support-boundary)
- [Validation](#validation)

- [Known Limitations and Follow-Up](#known-limitations-and-follow-up)

## Highlights

- Provides a shared read-only CLI for local development, pre-commit, and CI checks.
- Checks local Markdown links, immutable GitHub Actions references, dependency consistency,
  Python-version policy, and dated release changelog entries.
- Adds configurable consumer policy, isolated test layers, and wheel/source-distribution checks.
- Separates routine validation from explicitly authorized GitHub release publication.

## Change Scope

This candidate introduces the `src/popo/` package, command-line entry points, consumer
configuration, tests, packaging, Make targets, optional hooks, and GitHub automation. Contributor
and release documentation explain the same interfaces and validation boundaries. The [changelog]
retains the detailed change list, including interpreter-selection and module-rename corrections.

Popo checks repositories; it does not deploy infrastructure or modify consumer files. Its own
development policy does not prescribe a consumer's programming language, cloud, or branching model.

## Compatibility and Configuration

The [initial scaffold] contained no installable CLI, so there is no prior tagged CLI interface to
migrate. Use `popo` or `python -m popo`; each check accepts `--root`. Consumer settings live under
`[tool.popo]` in the inspected repository's `pyproject.toml`. See the [README] for commands,
dependency modes, and configuration examples.

`check-all` combines Markdown, action-pin, dependency, and Python-policy checks. Release-changelog
validation is separate and requires a release argument, for example `popo check-release-changelog
v0.1.0`. It expects a dated heading such as `## [0.1.0] - 2026-09-24`; retain the brackets required
by this checker.

## Support Boundary

The package declares Python 3.13 and 3.14 support and alpha development status. Some checks are
specific to Python metadata or GitHub Actions; language- and cloud-neutral design does not imply
that every ecosystem is already supported. Checks require no cloud credentials.

Make-based contributor workflows require Make and a POSIX-compatible shell. Cross-platform package
installation tests are distinct from those local tooling requirements; see the [contributing guide].

## Validation

The final candidate commit has not been recorded here. Before tagging, record that commit and
completed evidence for:

- `make check` and `make docs-markdown`;
- `make release-changelog RELEASE_VERSION=v0.1.0`;
- `make check-release`, including wheel and source-distribution builds, `twine check`, and clean
  installation tests against those same artifacts; and
- The applicable hosted validation matrices and artifact-integrity checks in the [release policy].

Passing checks on a development checkout are not evidence that the eventual tagged artifacts pass.
This record does not claim completed distribution validation or publication.

## Deployment and Rollback

Merging does not deploy cloud resources. Pushing an annotated version tag triggers CD validation;
GitHub publication requires the separate manual opt-in and safeguards in the [release policy]. No
workflow publishes to PyPI. Documentation alone does not enable hosted protections or publication.

Checks are read-only, so running them requires no consumer-data rollback. If adopting this candidate
blocks a consumer workflow unexpectedly, restore that consumer's previous tool configuration while
investigating and prepare a corrected candidate or follow-up version. Do not move a released tag.
The `v0.0.0` scaffold is not an installable package rollback target.

## Known Limitations and Follow-Up

- Markdown validation checks local links and anchors, not external URL availability.
- Confirm the final candidate commit, release date, artifact validation, and hosted protection
  settings before marking this record released.
- GitHub Release notes are generated by CD rather than automatically read from this file; reconcile
  published notes with this record when publication is authorized.
