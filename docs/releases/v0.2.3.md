# Popo v0.2.3

Planned patch release, prepared on 2026-09-27 from `feature/align-contributor-and-test-guidance`.
This release aligns contributor and test documentation while preserving Popo's generic, read-only
CLI behavior. It covers all four branch commits since `v0.2.2`; see the [changelog]. No tag or
publication is asserted by this record.

- [Highlights](#highlights)
- [Change Scope](#change-scope)
- [Compatibility and Configuration](#compatibility-and-configuration)
- [Support Boundary](#support-boundary)
- [Validation](#validation)
- [Deployment and Rollback](#deployment-and-rollback)
- [Known Limitations and Follow-Up](#known-limitations-and-follow-up)

## Highlights

- Map change types to focused Make validation targets in the agent instructions.
- Explain why passing source tests or prebuilt-artifact tests does not prove artifact creation.
- Clarify release-record ownership and shared pytest fixture contracts.

## Change Scope

The [agent instructions] now state existing conventions for Git-derived versions, intentional
package exports, NumPy-style docstrings, deterministic tests, pinned actions, and least-privilege
permissions. The validation table distinguishes unit/integration checks from distribution builds,
clean installations, and release gates without importing AWS-specific operations.

The [release notes template] links to the archive and distinguishes committed candidate records from
tagging and publication. Docstrings in `tests/conftest.py` and `tests/support/artifacts.py` describe
fixture inputs and outputs, layer classification, filesystem and subprocess failures, temporary-file
behavior, build isolation, prebuilt-artifact selection, and Twine validation.

## Compatibility and Configuration

No consumer compatibility or configuration changes. CLI commands, flags, diagnostics, exit codes,
and runtime validation are unchanged. Fixture implementations, test selection, workflow behavior,
and publication permissions are also unchanged. The new guidance documents existing commands; it
does not install hooks, configure hosted protections, or introduce a migration requirement.

## Support Boundary

No support-boundary or dependency changes. Python remains `>=3.13,<3.15`, and the runtime
dependency remains `packaging>=26.3,<27`. Artifact tests may download dependencies, but ordinary
repository checks remain read-only and independent of cloud credentials.

## Validation

Preparation baseline: commit `e62b69ddf486a12b9578309d8b5107be75c84b66`, plus these release-document
changes. The final release commit and tag are not yet established.

During branch development on macOS with Python 3.14.7, before these release documents were added:

- `make check` passed all 215 unit/integration tests, lint, formatting, strict typing, and
  repository self-checks.
- `.venv/bin/python -m pytest tests/meta tests/e2e` passed all 14 distribution and installation
  tests, exercising build-on-demand and validating the same temporary artifacts across both layers.
- Markdown link checks and `git diff --check` passed during the documentation updates.

Validate the new documents with `make release-changelog RELEASE_VERSION=v0.2.3` and `make
docs-markdown`. Before tagging, run `make check-release` with a fresh `PYTHON_DIST_DIR`, record the
final candidate commit, and complete the hosted gates in the [release policy]. Prior local results
do not establish cross-platform CI success or the tagged wheel's version match.

## Deployment and Rollback

No cloud deployment, data migration, or PyPI publication is introduced. Authorized tagging triggers
release validation; optional GitHub publication retains its manual opt-in and environment gates. Do
not move existing tags to incorporate documentation corrections.

Correct inaccurate guidance in a subsequent commit and release. Reverting these documentation
changes removes explanatory detail but does not reverse a runtime or test behavior change.

## Known Limitations and Follow-Up

- Documentation describes expected validation; it does not establish hosted configuration or
  publication outcomes.
- Confirm the final date and commit, complete the release gates, and update the archive status from
  verified results before claiming release completion.
