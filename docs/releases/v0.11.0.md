# Popo v0.11.0

Version 0.11.0 extends consumer-owned Python, Swift and log guardrails with optional source checks,
Swift toolchain declarations and stricter failure diagnostics. This minor release record is dated
2026-10-26 and prepared in released form at the maintainer's request. Tagging and publication are
separate operations and have not been performed by this preparation.

## Highlights

See the [changelog] for the complete dated scope, [source and log checks] for source conventions and
redacted diagnostic matching, and [Swift toolchain policy] for compiler declaration parity. Consumer
policy remains explicit; checks inspect files without executing inspected source or installing
consumer tools.

## Change Scope

Add opt-in `check-python-source`, `check-swift-source` and `check-logs`, using confined discovery,
consumer-owned limits, source-guide checks and existing text/JSON reporting. Python uses AST facts
and NumPy-style documentation; Swift uses bounded lexical declarations and DocC fields. Share
immutable declaration, callable-requirement and documentation evidence while preserving purposeful
language differences, syntax limits, ordering and redaction.

Add `check-swift-policy` with independent configuration, stable compiler selections, a preferred
local version, the package tools minimum and scoped CI observations. Swift is never invoked. Python
policy keeps dependency-derived defaults and legacy text workflow parsing; an optional
`workflow-parser = "scoped"` uses the shared strict YAML observer.

Correct quoted Python non-value return annotations, canonical package-name comparisons, log-root
resolution errors, malformed Markdown URLs and malformed inventory blob headers. Continue
independent automation, orphan-template and safety checks after discovery errors. Preserve carriage
returns and line feeds in Git-discovered header filenames and read template JSON explicitly as
UTF-8. Reject non-ASCII release-version digits, multiline log literals and whitespace in template
placeholder refs.

Separate parsing, discovery and orchestration boundaries in configuration, CLI, source inventory and
hosted auditing. Assemble actionlint replacements from original spans once, retain source snapshots,
index hosted approval scopes and use named immutable safety exceptions. Preserve comments and
contract details while aligning Python/Swift abstractions and docstrings. Configuration unit suites
now live under `tests/unit/config/`, matching `src/popo/config/`.

## Compatibility and Configuration

The documented scope includes new optional capabilities, so v0.11.0 advances the minor version from
v0.10.0. Versioning remains Git-derived through setuptools-scm; no independent version constant is
introduced. Existing baseline check selection remains unchanged unless an opt-in table, explicit
checks or profile selects another domain. Package-root exports are unchanged.

Use `python-source`, `swift-source`, `swift-policy` and `logs` policy tables and the documented
profile selection. Source limits use `documentation-width` and `max-file-lines`. Source-guide checks
require exact backticked relative paths. Log findings retain only filenames, line numbers and rule
IDs; each matching rule reports once per line in configured order.

### Breaking Changes

Stricter validation rejects previously accepted but ineffective multiline log patterns, whitespace
in template placeholder tokens and mixed Unicode release digits. Replace these with single-line
literals, whitespace-free tokens and ASCII release components. The earlier development names
`check-swift-documentation`, `swift-documentation`, `docstring-width` and `max-module-lines` have no
compatibility aliases; update consumer policy to the names above if those development forms were
adopted. Review consumer policy against the prior verified pin before rollout.

No runtime drop, publication change or package-root export removal is introduced by this
preparation.

### Deprecations

No additional deprecation window or stable-line support commitment is introduced. Development-name
migration is described above; unsupported aliases are not silently accepted.

## Support Boundary

Popo requires Python >=3.13,<3.15. Python and Swift consumer policies remain independent of Popo's
own interpreter constraints. Swift checks are declaration-only and bounded lexical checks, not
compiler, SwiftSyntax or full DocC validation. Python source checks observe annotations rather than
performing type checking. CI references are not evaluated as arbitrary expressions.

Default deterministic checks need no credentials or deployed services. Hosted auditing and external
actionlint execution remain explicit operations outside `check-all`; artifact builds/installations
may resolve declared dependencies. Local results do not establish cross-platform hosted success.

### Artifact Contracts

The wheel and sdist retain the `popo` distribution, `popo` console command and `python -m popo`
entry point. Native JSON reporting remains separate from source-inventory evidence and hosted-audit
output. No package publishing, release tag, workflow dispatch or hosted setting change is included.
Build metadata remains Git-derived; untagged artifacts must not be described as tagged v0.11.0
artifacts or as proof of publication. Validate the final committed/tagged tree before delivery.

## Deployment and Rollback

Follow the [release policy] and [release operations] for separately authorized tagging and optional
publication. Existing tags remain immutable. This preparation does not create a tag or publish a
package, and documentation status does not establish a hosted release outcome.

No consumer data migration is required. Adopt optional checks through reviewed consumer policy and
one explicit profile shared across entry points. To roll back adoption, restore the prior verified
pin and policy together. Do not retarget release tags or assume a local build is the released wheel.

## Known Limitations and Follow-Up

Complete final committed-tree packaging, tag/version agreement and supported Python/platform hosted
checks before delivery. Source convention checks, source inventories and approval attestations do
not establish code correctness, dependency completeness or release authorization. Retain compiler,
consumer integration and hosted checks appropriate to each repository.
