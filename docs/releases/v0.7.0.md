## Candidate and Highlights

Planned v0.7.0 candidate, prepared on October 22, 2026 (America/New_York). The dated [changelog]
entry identifies intended scope, not a completed release. Markdown consumers can consolidate local
reference-label and inline-image checks into the existing public `check-docs` command.

## Change Scope

Validate inline image destinations using the existing repository-containment rules. Reject
undefined full/collapsed reference labels and conflicting destinations after case and whitespace
normalization. Ignore inline code and HTML comments without losing original diagnostic line
numbers; comment delimiters inside code examples remain literal. Expand regression and installed
CLI coverage. The release-record gate accepts `release/prepare-MAJOR.MINOR.PATCH` while retaining
legacy release names and dated-record validation. No tools fetch external documentation or modify
consumer files.

## Compatibility and Support

### Breaking Changes

`check-docs` and `check-all` become stricter: previously accepted undefined labels, conflicting
reference definitions and missing or escaping inline images now fail with exit status one. Repair
those Markdown sources before upgrading. CLI commands, flags, configuration and success/failure
status conventions are unchanged. Generated heading IDs require no HTML anchor tags.

### Deprecations

None. Shortcut references and nested/escaped link syntax remain incompletely parsed; this is a
bounded checker rather than a complete Markdown renderer or an external URL checker.

### Support Boundary

Python remains `>=3.13,<3.15`, with unchanged runtime dependency bounds. Separate Python 3.15 work
is excluded. Local validation covers macOS with Python 3.13 and 3.14; hosted Linux/Windows execution
and tagged artifacts must be verified separately.

## Validation and Artifacts

The implementation passed 453 unit/integration tests on Python 3.13 and 3.14, lint, formatting,
strict typing and repository checks. On Python 3.14 it passed two artifact tests and 24 installed
CLI tests using freshly built wheel and source distributions. Pre-commit and the existing Swift
app consumer's Markdown check also passed. Release-record edits are included in the final candidate
validation; passing development builds do not establish a released version.

Wheel/sdist formats, console/module entry points, metadata, typing marker and license contracts
are unchanged. The CD workflow builds one artifact pair, validates installation, checks tag/version
agreement, generates a runtime SBOM and checksums, and retains artifacts for 14 days. An eventual
published GitHub Release may attach those artifacts through the opt-in protected publication job.

## Publication and Rollback

Not tagged or published. Reviewed PR integration is required before an annotated release tag can
be reachable from `main`. `develop` requires one approval; `main` requires two approvals with
code-owner review. Do not bypass those protections or change publication settings to finish this
candidate. Follow the [release policy] for tagged validation and optional publication.

Consumers should retain their released immutable dependency pin until validation and release
complete. Roll back an adoption by restoring the previous pin and its complementary local checks;
do not move or replace a release tag.

## Follow Up

Obtain the configured reviews, merge the candidate through reviewed integration, validate its
annotated tag and hosted CI/CD artifacts, and record actual publication evidence. Only then replace
consumer-side compatibility checks and label the dependency as released.
