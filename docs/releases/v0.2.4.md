# Popo v0.2.4 (Planned)

Version 0.2.4 standardizes, tagged on 2026-09-27, Popo's historical release records while preserving
their original scope and preparation-time evidence. It covers the complete change scope since
`v0.2.3`; see the [changelog].

- [Highlights](#highlights)
- [Change Scope](#change-scope)
- [Compatibility and Configuration](#compatibility-and-configuration)
- [Support Boundary](#support-boundary)
- [Validation](#validation)
- [Deployment and Rollback](#deployment-and-rollback)
- [Known Limitations and Follow-Up](#known-limitations-and-follow-up)

## Highlights

- Identify tagged historical releases consistently with their verified dates and tag status.
- Preserve preparation-time validation statements without presenting them as post-tag evidence.
- Connect each versioned record to its dated changelog entry and the release archive.

## Change Scope

The versioned records from `v0.0.0` through `v0.2.3` now use consistent file descriptions and
maintainer guidance. Records for tagged releases identify the tag date and status while explicitly
retaining pending checks and candidate references as historical preparation-time evidence. Changelog
links now target each release's dated section, and records link back to the [release archive] where
applicable.

These documentation corrections do not rewrite existing tags or assert unverified validation or
publication outcomes. Package source, tests, dependencies, automation, and configuration are
intentionally unchanged.

## Compatibility and Configuration

No compatibility or configuration changes. CLI commands, flags, diagnostics, output, exit codes,
and `[tool.popo]` configuration are unchanged. No consumer or maintainer migration is required.

## Support Boundary

No support-boundary changes. Python remains `>=3.13,<3.15`, and the runtime dependency remains
`packaging>=26.3,<27`. Internal checker modules remain outside the promised public API.

## Validation

This record was prepared after the historical release-document standardization and alongside this
changelog and archive update. The final release commit and tag are not yet established.

Against that baseline plus the release-document changes:

- `make release-changelog RELEASE_VERSION=v0.2.4` passed.
- `make docs-markdown` passed, including local Markdown link validation.
- `make check` passed Ruff lint and formatting, strict typing, all 215 unit/integration tests, and
  all configured repository checks.

Before tagging, run `make check-release` with a fresh `PYTHON_DIST_DIR`, record the final candidate
commit, and complete the hosted gates in the [release policy]. Checks against the working tree do
not establish cross-platform CI success, tagged artifact integrity, or publication.

## Deployment and Rollback

No cloud deployment, data migration, or PyPI publication is introduced. Authorized tagging
triggers release validation; optional GitHub publication retains its manual opt-in and environment
gates. Existing tags must not be moved to incorporate these documentation corrections.

If a record remains inaccurate, correct it in a subsequent commit and release. Reverting this
documentation-only change has no runtime or consumer-data effect.

## Known Limitations and Follow-Up

- Complete the release gates against the final candidate before tagging.
- Update the archive status only from verified tag, validation, and publication evidence.
